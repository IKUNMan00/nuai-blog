## 三、技术收获

### 3.1 后端：从“写路由”到“分层”

【写一个具体的技术点，不要泛泛而谈。建议从应用工厂、蓝图、ORM、权限、事务中选一个。】

示例：

> 以前我把所有路由写在一个 `app.py` 里，变量和数据库连接都是全局的。这个项目第一次用应用工厂和蓝图：`create_app()` 负责装配，`main/auth/admin/api` 各自管一块。最开始我不理解为什么要多这一层，直到写测试时发现可以给测试单独注入 SQLite 配置，才意识到它的价值。后来我又把文章表单校验抽成 `_validate_post_form()`，路由函数明显变短，也更容易补测试。

### 3.2 数据库：从“能存”到“存得对”

【写一个具体设计取舍，如联合主键、外键级联、索引、冗余字段。】

示例：

> 收藏表最初我加了自增主键，后来发现同一用户可能重复收藏同一篇文章。改成 `(user_id, post_id)` 联合主键后，重复插入会直接被数据库拒绝，业务层也少了一次“先查再插”的判断。另一个取舍是 `posts.view_count`：它和 `post_views` 明细表看起来冗余，但热门排序需要汇总值，每次都 `COUNT` 会很慢，所以保留了这个冗余字段。

### 3.3 前端：从“堆样式”到“设计系统”

【写 CSS 变量、响应式、可访问性、原生 JS 中的一点。】

示例：

> 我以前写暗黑模式是复制一套 CSS 再改颜色，维护起来很痛苦。这次用 CSS 自定义属性，把颜色、阴影、圆角定义在 `:root`，暗黑模式只覆盖变量。新增组件只要用变量就自动适配。这个过程让我理解了“设计令牌”不是设计师的概念，而是前端可维护性的基础。

### 3.4 安全：从“没见过”到“会防御”

【写 XSS、CSRF、越权、上传中的一点。】

示例：

> 做 Markdown 预览时，我一开始直接 `innerHTML = marked(...)`，后来意识到这等于允许用户注入脚本。改成后端 Python-Markdown 渲染后再用 bleach 白名单过滤，并且只对文章正文使用 `|safe`。我们还补了一个测试，输入 `<script>` 后断言输出里没有脚本标签。这让我第一次真正理解“永远不要信任用户输入”。

### 4.2 我遇到的协作问题与解决

| --- | --- | --- |

## 五、遇到的问题与解决过程

> 选 1–2 个真实问题，写清楚“现象 → 排查 → 原因 → 解决 → 验证”。不要只写“百度了一下就好了”。

### 问题 1：【例如：文章列表查询出现 N+1】

- **现象**：列表只有 6 篇文章，却执行了 20 多条 SQL；
- **排查**：打开 SQLAlchemy echo，发现每条文章都单独查分类和作者；
- **原因**：模板访问 `post.category.name` 时触发懒加载；
- **解决**：列表查询加 `joinedload(Post.category)`、`joinedload(Post.author)`、`selectinload(Post.tags)`；
- **验证**：SQL 数量下降，页面渲染正常，测试通过。
