## 0. 路演总策略

不要按“技术栈 → 数据库 → 每个页面”流水账讲。课堂评委最关心三件事：

1. **你们解决了什么问题？**（选题价值）
2. **系统真的能跑吗？**（现场演示 / 录屏）
3. **你们是怎么把它做出来的？**（设计、协作、测试）

因此采用「**问题 → 方案 → 演示 → 工程 → 反思**」结构：

```text
Cover
1 选题背景与目标
2 用户角色与核心场景
3 需求范围：主体 + 扩展
4 技术选型与总体架构
5 数据库设计
6 视觉与页面规划
7 主体功能演示动线
8 扩展功能：Markdown 编辑器
9 扩展功能：评论审核与收藏
10 扩展功能：图片附件与数据看板
11 关键代码与技术难点
12 测试与质量保障
13 部署与 GitHub 协作
14 项目成果与不足
15 总结与展望 / Q&A
```

## 1. 逐页大纲

### Slide 1 · 封面

**画面**

- 左侧：大标题「我的知识小栈」，副标题「个人博客 / 笔记管理系统」
- 右侧：首页 Hero 截图或层叠便签插画
- 底部：课程名称、小组名称、成员、日期

**讲稿（15 秒）**

> 大家好，我们是第 X 组。我们的项目叫「我的知识小栈」——一个把零散学习笔记收进一座会生长的个人博客系统。下面用 8 分钟介绍我们做了什么，以及为什么这样做。

**设计**

- 米白背景 + 深绿大标题 + 陶土色小标签；
- 右上角放 `EST. 2026` 印章；
- 不堆成员照片，姓名用一行小字。

### Slide 2 · 选题背景：为什么需要一座“小栈”？

**画面**

三栏痛点卡片：

1. **找不到**：收藏夹、聊天记录、本地文档分散；
2. **留不住**：只收藏不加工，经验无法复用；
3. **讲不清**：项目做完没有结构化复盘。

底部一句结论：**我们需要的不只是“记事本”，而是一条“收集—加工—输出”的闭环。**

**讲稿（35 秒）**

> 我们都有过这样的经历：明明之前解决过某个报错，却怎么也找不到当时的记录；收藏了几百篇文章，真正用上的没几篇。问题不是工具不够多，而是缺少一个自己的知识入口。所以我们想做一个真正会用的个人博客 / 笔记系统，而不是为了交作业临时拼一个 CRUD。

### Slide 3 · 用户角色与核心场景

**画面**

三列角色卡：

| 访客 | 注册读者 | 博主 |
| --- | --- | --- |
| 浏览、搜索、游客评论 | 收藏、账号评论、我的评论 | 发文、分类标签、审核、看板 |

底部一条主场景时间线：

```text
写笔记 → 分类打标 → 发布 → 被搜索/阅读 → 收到评论 → 审核 → 看板复盘
```

**讲稿（35 秒）**

> 我们把角色收敛成三类。访客不需要注册就能读和留言；注册读者可以收藏、用账号评论；博主是唯一的内容管理者。这样既保留了注册流程，又符合个人博客“一个站主 + 多位访客”的真实语义，避免任何人注册就能进后台。

### Slide 5 · 技术选型与总体架构

**画面**

技术栈徽章：

```text
Flask 3 · MySQL 8.0 · SQLAlchemy · Jinja2 · 原生 CSS/JS · Docker
```

右侧架构图（简化）：

```text
浏览器
  ↓
Flask（main / auth / account / admin / api）
  ↓
SQLAlchemy ORM
  ↓
MySQL 8.0 + 本地附件目录
```

底部三条选型理由：

- Flask 轻量，适合课程讲解与快速部署；
- 原生前端，不引入框架，降低理解成本；
- MySQL 独立部署，符合课程要求。

**讲稿（40 秒）**

> 技术栈刻意保持简单。后端 Flask，数据库 MySQL 8.0，前端是服务端渲染加原生 JS。没有 Vue/React，也没有 Redis 和微服务。不是不会，而是当前项目不需要——我们希望每一行代码都能在答辩时讲清楚为什么存在。

### Slide 6 · 数据库设计：9 张表，关系清晰

**画面**

简化 ER 图：

```text
users 1─N posts N─N tags
         │ 1
         ├─N comments
         ├─N favorites
         └─N post_views
categories 1─N posts
users 1─N attachments
```

右侧设计亮点：

- `utf8mb4` 支持中文与 emoji；
- 文章同时保存 Markdown 与安全 HTML；
- 收藏联合主键防重复；
- `post_views` 明细 + `view_count` 汇总；
- 评论状态机 `pending/approved/rejected`；
- 分类删除 `SET NULL`，文章不丢。

**讲稿（45 秒）**

> 数据库一共 9 张表。核心是 users、posts、categories、tags，以及评论、收藏、附件、浏览明细和文章标签关联表。这里有两个我们比较满意的取舍：第一，文章同时存 Markdown 原文和过滤后的 HTML，编辑用原文、展示用 HTML；第二，浏览量既有汇总字段方便排序，又有明细表支撑 7 日趋势。

### Slide 7 · 视觉与页面规划：像“自己的地方”

**画面**

首页截图（大）+ 三个小图：详情页、后台看板、手机端。

三个关键词：

- **纸张感**：米白、细网格、层叠便签；
- **统一**：一套 CSS 变量覆盖 20+ 页面；
- **双主题**：浅色 / 暗黑，刷新保持。

**讲稿（35 秒）**

> 视觉上我们不想做成通用后台模板。用了米白纸感、深绿主色和陶土色点缀，标题用衬线字体，希望像一个有人认真整理的地方。所有页面共享一套 CSS 变量，所以暗黑模式不是复制一套样式，而是换一组变量。手机端也做了完整适配。

### Slide 8 · 主体功能演示动线

**画面**

四步流程 + 对应截图：

```text
① 前台搜索 / 分类筛选
② 登录博主 → 写文章
③ 发布 → 前台详情
④ 编辑 / 转草稿 / 删除
```

**讲稿（45 秒）**

> 主体功能我们用一条动线演示：先在首页搜索 Flask，看到分类和标签筛选；然后登录博主，在后台写一篇新文章，选分类、打标签、发布；回到前台，文章出现在列表和详情；最后演示编辑、转草稿和删除。整个过程不需要重启服务，数据实时生效。

**演示提示**

- 提前开好两个浏览器窗口：前台 + 后台；
- 搜索词用 `Flask`，稳定命中；
- 新文章标题带时间，便于识别；
- 删除操作只删演示文章。

### Slide 9 · 扩展一：Markdown 编辑器

**画面**

编辑器截图：左侧 Markdown、右侧预览、工具栏、图片上传。

三个技术点：

1. 320ms 防抖 + 后端渲染；
2. Python-Markdown + bleach 白名单；
3. 粘贴 / 拖拽图片自动插入。

**讲稿（40 秒）**

> 编辑器不是简单放一个 textarea。左侧写 Markdown，右侧实时预览，带工具栏和快捷键。预览不是前端随便渲染，而是走后端统一渲染并做 bleach 白名单过滤，保证预览和最终详情一致，也避免存储型 XSS。图片可以点按钮、粘贴或拖拽上传，自动插入 Markdown。

---

### Slide 10 · 扩展二：评论审核与收藏

**画面**

评论状态机：

```text
pending → approved / rejected
```

收藏：

```text
读者点击收藏 → favorites 联合主键 → 我的收藏分页
```

两条设计说明：

- 评论默认不公开，审核后才展示；
- 蜜罐 + 20 秒限频 + 纯文本输出。

**讲稿（35 秒）**

> 评论采用“先审后发”。访客和读者都能留言，但默认进入待审核，后台可以通过、驳回、删除。为了防止简单刷评论，加了蜜罐字段、20 秒限频和长度校验。收藏用联合主键防重复，读者在账号中心能看到自己的收藏列表。

---

### Slide 11 · 扩展三：图片附件与数据看板

**画面**

左侧附件库截图，右侧看板截图。

附件：

- Pillow 真实解码，拒绝伪装图片；
- UUID 重命名，5MB 限制；
- 复制 Markdown / URL。

看板：

- 文章数、阅读、今日/7 日、待审评论、收藏；
- 7 日柱状图、分类环形图、热门文章、最新动态。

**讲稿（40 秒）**

> 图片上传不信任扩展名，用 Pillow 真正解码，只接受 JPEG/PNG/GIF/WEBP，UUID 重命名，防止脚本伪装和覆盖。看板展示文章、阅读、评论、收藏，以及近 7 天趋势和分类分布。图表是纯 CSS 实现的，不依赖 Chart.js，断网也能演示。

### Slide 12 · 关键代码与技术难点

**画面**

四张代码卡：

1. **应用工厂**：测试可注入 SQLite；
2. **权限校验**：后台统一 `before_request`；
3. **安全渲染**：Markdown → bleach；
4. **查询优化**：joinedload / selectinload。

底部一句：**“能跑”之外，我们更关心“为什么这样写”。**

**讲稿（45 秒）**

> 这里挑四个点。第一，应用工厂让测试可以注入独立数据库；第二，后台权限统一在 before_request 校验，不依赖模板隐藏；第三，Markdown 渲染后必须过 bleach，正文是唯一使用 safe 的地方；第四，列表查询用 joinedload 和 selectinload 预加载，避免 N+1。这些是课程项目里最容易踩、也最值得讲的点。

### Slide 14 · 部署与 GitHub 协作

**画面**

左侧部署：

```bash
docker compose up -d --build
# 前台 :5000 / MySQL :3307
```

右侧协作：

- `main` 保护 + `develop` 集成；
- `feature/*` 短分支；
- Conventional Commits；
- PR 模板 + 至少 1 人评审 + CI；
- Issue / Projects 看板。

底部：**一条命令启动，五个人并行不打架。**

**讲稿（40 秒）**

> 部署上提供 Docker Compose，一条命令启动 MySQL 和应用，首次自动建表并生成演示数据。协作上采用简化 Git Flow：main 保护、develop 集成、feature 短分支，提交遵循 Conventional Commits，PR 必须过 CI 和至少一人评审。这样五个人并行开发时，冲突和回滚都可控。

### Slide 15 · 项目成果与不足

**画面**

成果数字：

- 9 张表、30+ 路由、20+ 页面；
- 主体 5 项 + 扩展 6 项；

**讲稿（35 秒）**

> 成果方面，我们完成了 9 张表、30 多个路由、20 多个页面，主体和扩展功能都能演示，测试和文档也齐全。也清楚不足：搜索还是 LIKE，数据量大要上全文索引；目前是单博主，没有多作者协作；图片存本地，生产可以换对象存储。这些不是“没想到”，而是课程周期内的主动取舍。

## 3. 演示动线（与 PPT 配合）

### 3.1 演示前 5 分钟检查

- [ ] `docker compose up -d` 或本机服务已启动；
- [ ] 前台、后台各开一个窗口；
- [ ] 已登录 admin，读者窗口未登录；
- [ ] 演示文章《从零搭建…》存在；
- [ ] 待审核评论至少 2 条；
- [ ] 图片上传目录可写；
- [ ] 网络/投屏分辨率确认；
- [ ] 录屏备份可播放。

### 3.2 演示脚本（与 Slide 8–11 对应）

| 步骤 | 操作 | 讲解 |
| --- | --- | --- |
| 1 | 首页滚动 | 视觉、置顶、分类、标签、统计 |
| 2 | 搜索 `Flask` | 标题/正文命中，组合筛选 |
| 3 | 打开文章 | 正文、目录、收藏、评论 |
| 4 | 游客评论 | 默认待审核，前台不显示 |
| 5 | 登录 admin | 进入后台看板 |
| 6 | 审核评论 | 通过 → 前台刷新可见 |
| 7 | 写新文章 | Markdown、预览、分类、标签、封面 |
| 8 | 发布 | 前台列表/详情出现 |
| 9 | 上传图片 | 附件库复制 Markdown |
| 10 | 切换主题/手机 | 双主题、响应式 |

### 3.3 演示兜底

- 如果数据库/网络异常：播放录屏，不现场修环境；
- 如果搜索无结果：改用分类筛选，不要连续试错；
- 如果上传失败：展示附件库已有图片，说明限制；
- 如果时间不够：跳过第 8 步发布，直接展示已发布文章。

## 5. PPT 制作规范

- 16:9，13.333 × 7.5 英寸；
- 标题字号 32–40，正文 14–18，注释 10–12；
- 每页一个核心观点，不超过 3 个要点；
- 截图加圆角/细边框，不拉伸变形；
