# 《我的知识小栈》答辩问答（20 问）

> 用法：不要背逐字稿，记住每题的“结论 + 理由 + 证据”。回答控制在 30–60 秒，遇到不会的坦诚说明，并给出排查思路。

---

## 一、选题与需求

### Q1：为什么选“个人博客 / 笔记管理”这个题目？是不是太简单？

**结论**：题目看似常见，但我们做的是完整闭环，不是单表 CRUD。

**理由**：

- 需求覆盖内容生产、组织、检索、互动、审核、统计、权限；
- 主体 5 项 + 扩展 6 项，包含 Markdown、评论状态机、附件安全、看板；
- 有真实使用场景：我们自己的课程笔记和项目复盘。

**证据**：功能清单、20+ 页面、9 张表、13 个测试。

---

### Q2：你们和普通的博客模板有什么区别？

**结论**：模板只解决“展示”，我们解决了“管理与安全”。

**理由**：

- 博主后台完整 CRUD、草稿/发布、分类标签、置顶；
- 评论先审后发，有状态和审核人；
- Markdown 服务端渲染 + XSS 过滤；
- 图片真实格式校验、UUID 存储；
- 数据看板、访问明细、会话去重；
- 双主题、响应式、可访问性。

---

### Q3：为什么公开注册的用户不是管理员？

**结论**：个人博客的产品语义是“一个站主 + 多位访客”，注册即管理员会造成严重越权。

**理由**：

- 公开注册固定 `role='reader'`，只能收藏、评论、管理自己的账号；
- 博主账号由 CLI 创建，或由现有管理员提升；
- 后台在 `before_request` 统一校验角色，不依赖模板隐藏。

**证据**：`auth.register` 中角色硬编码；`test_reader_cannot_access_admin` 断言 403。

---

### Q4：你们的需求优先级是怎么定的？

**结论**：P0 先闭环，P1 加分，P2 可裁剪。

**理由**：

- P0：登录、文章 CRUD、分类标签、浏览分页、搜索；
- P1：Markdown、收藏、评论审核、双主题、上传、看板；
- P2：账号中心细节、额外动效；
- 先保证“能发文 → 能读到 → 能互动 → 能管理”，再做视觉与统计。

---

## 二、技术与架构

### Q5：为什么选 Flask，不用 Spring Boot / Django？

**结论**：课程项目需要轻量、易讲、易部署，Flask 更合适。

**理由**：

- 路由与模板直观，适合课堂讲解；
- 生态足够，Flask-Login / SQLAlchemy / Flask-WTF 覆盖需求；
- 启动快，Docker 镜像小；
- 我们不是为了“企业级”而堆技术，而是匹配项目规模。

**补充**：如果需求变成多模块、强事务、复杂权限，Spring Boot 会更合适；这是取舍，不是优劣。

---

### Q6：为什么前端不用 Vue / React？

**结论**：课程明确要求原生前端，且博客以内容展示为主。

**理由**：

- 服务端渲染对 SEO、首屏、权限更友好；
- 原生 JS 足以完成主题、弹窗、编辑器、上传；
- 少一层构建工具，部署和讲解都更简单；
- 我们做了渐进增强：JS 失败仍可浏览和提交表单。

---

### Q7：为什么要用应用工厂 `create_app()`？

**结论**：为了可测试、可配置、避免全局状态。

**理由**：

- 测试可以注入独立 SQLite 和上传目录；
- 配置从环境变量读取；
- 蓝图在工厂内注册，避免循环导入；
- 同一套代码可跑开发/测试/生产。

**证据**：`tests/conftest.py` 用 `create_app({...})` 创建独立应用。

---

### Q8：蓝图的划分依据是什么？

**结论**：按业务边界和权限边界划分。

**理由**：

- `main`：公开站点；
- `auth`：认证；
- `account`：登录用户账号中心；
- `admin`：博主后台；
- `api`：JSON 接口。

这样五个人可以并行开发，减少文件冲突；权限也在蓝图层统一处理。

## 三、数据库

### Q9：为什么文章同时存 `content_md` 和 `content_html`？

**结论**：编辑需要原文，展示需要安全 HTML，冗余换性能与稳定。

**理由**：

- 每次访问重新渲染浪费 CPU；
- 渲染器升级可能影响历史文章展示；
- 搜索用 Markdown 原文；
- HTML 已过滤，展示直接用。

**代价**：存储翻倍、需要保证两者同步；在课程项目中可接受。

---

### Q10：为什么 `view_count` 和 `post_views` 同时存在？

**结论**：汇总 + 明细。

**理由**：

- `view_count` 用于热门排序，避免每次 `COUNT` 全表；
- `post_views` 用于 7 日趋势和单篇分析；
- 当前没有做定时对账，生产可以每天校准一次。

---

### Q11：收藏表为什么用联合主键？

**结论**：从数据库层防止重复收藏。

**理由**：

- `PRIMARY KEY (user_id, post_id)` 天然唯一；
- 不依赖“先查再插”的应用逻辑，避免并发重复；
- 两个外键都加索引，兼顾按用户查和按文章统计。

---

### Q12：为什么分类删除是 `SET NULL`，文章删除是 `CASCADE`？

**结论**：分类是“归类”，文章是“主体”。

**理由**：

- 删除分类不应删除文章，文章可以变成未分类；
- 删除文章时，评论、收藏、浏览记录依附于文章，应一并清理；
- 评论的用户外键用 `SET NULL`，保留内容，避免用户注销导致讨论消失。

## 四、安全

### Q13：如何防止存储型 XSS？

**结论**：服务端白名单过滤 + 唯一 `|safe` 入口 + 测试。

**链路**：

```text
Markdown → Python-Markdown → bleach.clean(白名单)
→ 存入 content_html → 详情页 |safe
```

- 只允许安全标签/属性/协议；
- 删除 script/style/iframe 等；
- 评论纯文本输出；
- 测试输入 `<script>` 断言不出现。

**注意**：前端预览也调用同一后端接口，避免两套渲染逻辑。

---

### Q14：如何防止 CSRF？

**结论**：Flask-WTF 全局 CSRFProtect。

**做法**：

- 所有 HTML POST 带 `csrf_token`；
- JS 请求带 `X-CSRFToken`；
- 登录、发文、删除、审核、收藏、上传全部覆盖；
- 测试环境关闭，生产开启。

---

### Q15：如何防止越权？

**结论**：服务端统一校验，模板隐藏只是体验。

**做法**：

- `admin_bp.before_request` 校验 `current_user.is_admin`；
- 账号中心 `before_request` 校验登录；
- 草稿详情只有博主可预览；
- API 单独校验博主；
- 测试覆盖读者访问后台 403。

---

### Q16：图片上传如何防止伪装脚本？

**结论**：不信任扩展名，真实解码 + 白名单 + 重命名。

**链路**：

1. 限制 5MB；
2. Pillow `verify()` 再打开；
3. 只接受 JPEG/PNG/GIF/WEBP；
4. UUID 重命名；
5. 保存到 `uploads/年/月`；
6. 删除时校验路径必须在 uploads 内。

**没有做**：图片内容深度扫描、CDN 隔离；生产可加。

## 五、功能与实现

### Q17：Markdown 预览和最终详情为什么能保持一致？

**结论**：两者调用同一个 `render_markdown()`。

**理由**：

- 预览接口 `api.markdown_preview` 调它；
- 保存文章时 `admin.post_new/post_edit` 调它；
- 同一套 Markdown 扩展与 bleach 白名单；
- 预览只是把结果返回到右侧，不另写前端解析。

---

### Q18：浏览量会不会重复？管理员预览算不算？

**结论**：同一会话同一篇只计一次，管理员预览不计。

**理由**：

- `session.viewed_posts` 保留最近 30 篇；
- 第一次访问才 `view_count += 1` 并写 `post_views`；
- 博主查看草稿/预览不计；
- 这是“课程项目可接受”的口径，不是精确 UV。

---

### Q19：搜索为什么用 `LIKE`？性能怎么办？

**结论**：当前数据量小，优先正确与简单；大数据量换全文索引。

**理由**：

- `LIKE '%关键词%'` 无法用普通 B-Tree；
- 课程数据量在千级以内，可接受；
- 已经在文档中给出 MySQL `FULLTEXT + ngram` 方案；
- 也可以通过分类/标签缩小范围。

**诚实**：这是已知不足，不是“最优方案”。

---

### Q20：如果让你继续做三个月，你会先改什么？

**结论**：先搜索，再部署与媒体，最后协作。

**顺序**：

1. 搜索：MySQL FULLTEXT + ngram，或 Meilisearch；
2. 部署：Nginx + HTTPS + 每日备份；
3. 媒体：对象存储、图片压缩、缩略图；
4. 内容：文章版本历史、定时发布、RSS；
5. 协作：多作者、角色细分、评论回复；
6. 性能：Redis 缓存首页/热门，浏览量原子自增。

## 附：现场演示翻车应对

| 情况 | 应对 |
| --- | --- |
| 数据库连不上 | 切到备用 SQLite/Docker，或播放录屏 |
| 搜索无结果 | 改用分类进入，不要连续试错 |
| 上传失败 | 展示附件库已有图片，说明 5MB/格式限制 |
| 评论被限频 | 等 20 秒或换浏览器会话，剪辑时删掉 |
| 登录过期 | 提前重新登录，不在演示中清 Cookie |
| 投屏比例不对 | 浏览器 100% 缩放，F11 全屏 |
| 时间不够 | 跳过发布，直接展示已发布文章和看板 |

## 附：回答结构模板

遇到没有准备的问题，用这个结构：

```text
结论：一句话回答。
理由：2–3 条，按重要性排序。
证据：代码位置 / 测试 / 页面 / 文档。
边界：当前没做什么，为什么；以后怎么改。
```

例：

> 结论：我们目前没有做全文索引。理由：数据量小，LIKE 足够，课程周期有限。证据：搜索在 `main.posts`，文档写了升级方案。边界：数据上万后会慢，下一步用 MySQL FULLTEXT + ngram。
